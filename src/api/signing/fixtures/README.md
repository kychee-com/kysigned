# Signing fixtures

## `m365-corporate-no-dkim.GENERATED.eml` (GENERATED MOCK, not real mail)

A made-up forward-to-sign from a signer at a company on **Microsoft 365 with DKIM
switched off** (F-45.1, AC-279). No such company was available to send a real one, and
only Microsoft's servers can make the seal the live service verifies, so this file is
generated by `scripts/gen-m365-no-dkim-mock.mjs`.

What it is:

- Exchange Online's header layout, modelled on a real Outlook forward (the
  `X-MS-Exchange-*` headers, Microsoft's ARC-Message-Signature header list, and the
  `mx.microsoft.com 1; spf=none; dmarc=none; dkim=none; arc=none` results line).
- **No DKIM-Signature**, which is how Microsoft documents mail from a custom domain
  without DKIM.
- One ARC set (`i=1`, `d=microsoft.com`, `s=arcselector10001`, `cv=none`) sealed by
  the real `mailauth` code with a **stand-in key**, made fresh on each run. Only its
  public half is kept, in `m365-corporate-no-dkim.GENERATED.json` under `standInKeys`.

How tests use it: a test resolver serves the stand-in key under Microsoft's key name
(`arcselector10001._domainkey.microsoft.com`), so the seal verifies and the forward is
diagnosed "Microsoft 365 without DKIM". Against any other key, including Microsoft's
real one, the seal fails. That is exactly how the live service would treat this file,
and a test pins it.

Everything in it is fictional: the people and the company use the reserved `.example`
domain, the envelope is invented, the attachment is a placeholder PDF, and the IP
addresses come from documentation ranges. The first header (`X-Kysigned-Fixture`), the
file names and the `.json` (`"generated": true`) all mark it as generated.

Regenerate (new key and seal; everything else stays the same):

    node --import tsx scripts/gen-m365-no-dkim-mock.mjs
